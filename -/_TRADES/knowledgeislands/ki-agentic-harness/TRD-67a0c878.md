# TRD-67a0c878: Trade workflow learnings

## Context

`tools-mgit` received and adopted a work trade from `tools-ki` while establishing its first local roadmap item. Applying the current `ki-trades` definition exposed the operational steps a receiver must perform manually before a companion process surface exists.

## Submission

Retain these observed requirements for the Harness trade-operation work:

- Start from the current repository's declared `imports_from` routes, then inspect only matching sender-owned records addressed to that repository. A local incoming directory alone shows received records, not all available imports.
- Validate the active typed route before preparing a local inbound copy. Keep receiving distinct from disposition: an inbound copy starts `unconsidered`; adoption needs a separately confirmed local work record and `adopted_as` linkage.
- Preserve the complete sender envelope and body byte-for-byte. The receiver may add only its allowed local fields.
- Account for a mechanical conflict: the repository-wide Markdown formatter rewrote an inbound sender payload's quote style and blank-line shape, after which the immutable-copy trade audit correctly failed. A trade-operation design needs an explicit formatter boundary that preserves sender bytes rather than silently normalising an inbound copy.
- Keep local roadmap capture separate from trade delivery and disposition. The receiving repository alone chooses its horizon, priority, plan, implementation, and acceptance.

## Constraints

This submission describes observed process evidence, not a request for a specific command design.
